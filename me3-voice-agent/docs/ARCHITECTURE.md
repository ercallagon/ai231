# Architecture and decisions

## Deployment boundary

Target hardware: Raspberry Pi 5 with 4 GB RAM. Validate CPU and memory use on this device when selecting local audio components and dependencies.

User reports the professor described the Pi as mostly hosting VAD. Pending clarification, interpret this as lightweight local audio/control and remote large-model inference; it does not by itself establish permission to relocate the harness or our speech MCP servers, which the supplied written specification places on Pi. A remote-harness/audio-client topology is technically viable if explicitly accepted. Do not silently migrate the deployment boundary or introduce an HPC runtime dependency.

The Pi owns the harness, session state, microphone capture, playback, local VAD, MCP client, and our ASR/TTS MCP servers. Task execution currently uses in-process typed adapters; a separate task MCP server is not implemented. A configured commercial API or authenticated shared model service may provide inference; neither hosting choice is assumed. A hosted conversational agent alone does not demonstrate this deployment boundary.

Target Pi flow (Pi device capture/playback and echo handling remain unimplemented):

```text
Microphone -> continuous audio capture -> echo handling -> wake/session controller
                                      -> local VAD -> our ASR server -> ASR adapter / configured backend
                                                        |
                                                  agent harness
                                                        |
                                              typed task adapters
                                                        |
                                                verified tool result
                                                        |
Speaker <- playback queue <- our TTS server <- TTS adapter / configured backend <- response text
```

The HPC implementation supports file input with a memory sink and a loopback browser transport with browser microphone/output. Both feed the same Session and local ASR/TTS MCP subprocesses; provider adapters remain behind those servers. Browser echo cancellation is requested, not verified. The browser transport is an HPC integration prototype and does not establish Pi device capture/playback or acoustic behavior.

## Conversation memory policy (verified 2026-11-05)

Session owns chat history. It appends accepted user text, typed action outcomes (including failed/unknown), and only sink-confirmed assistant segments. Authoritative late completion may settle its own Unknown action record; stale generation cannot append a new reply. Ending engagement retains the old history for evidence only; the next activation clears history and starts a fresh session ID. Browser reconnect/new Session/process restart does not restore chat from transcript files or SQLite. A visible saved transcript is not model context. Shared device/service state is intentionally separate from conversation scope; there is no authenticated multi-user profile isolation.

OnitPrimaryReasoning now sends complete ordered dialogue and compact structured task outcomes within the existing 8,000-character task-input contract. It no longer silently keeps only ten messages or clips each message at 1,600 characters. Previous Onit prompt arguments are not recursively embedded. If complete available context exceeds the contract, it fails with context_capacity and guidance to start fresh; there is no extra summarization request. Direct ChatReasoning retains its existing messages/music-focus projection, so provider context and UI transcript are not interchangeable. The canonical retention/recovery matrix is in PLAN.md's 2026-11-05 memory-audit section.

UI theme, engagement mode and selected-report ID use existing browser localStorage by origin; spoken facts are not persisted as preferences. Current/per-session transcript files and opt-in durable action records remain evidence/task stores, not learned personal memory. No new transcript/audio retention or vector store was introduced. Session history/events still grow over a long connection; diagnostic collections and UI projections retain their existing bounds. Recovered exact-ID action receipts are visual-only and never themselves trigger narration, dispatch or restored timer widgets.

The earlier authorized live draft task timed out with no files. Experiment 020 later repeated task-shaped requests after restoring durable attempt accounting; see its latest status below. Neither set qualifies generated project output or contextual reasoning. Future workers retain payload-free pre-transmission attempt ordinals/timestamps in their private task workspace, including failure cases. These counters are attempts, not proof of accepted/billed provider requests.

## Receipt recovery boundary (experiment 019 continuation)

The existing device/music executor optionally accepts `voice_bridge --receipt-store var/cache/task-receipts.sqlite3`. SQLite commits intent before dispatch and a result before delivery. Exact UI command IDs can recover across process restart; original voice session/turn/call IDs remain their scope. Arguments and adapter target context are hashed; credentials/raw requests are not stored. Pending records are Unknown and never automatically replayed, because a crash may occur before or after an external effect. Completed records return historical receipts without active-state widgets. Timers are not rearmed after process death. This does not guarantee exactly-once external effects, automatic browser/session restoration, or Onit general-task recovery. The flag is off by default. The local `me3_voice.receipts inspect --store ...` CLI is read-only.

A live Session can observe an already-owned device/music operation's completion and settle only its corresponding Unknown receipt, preserving newer tasks and emitting no replacement speech. Fresh Spotify pause/stop read-back can describe current provider state after lost acknowledgment, without proving acoustic output or causal completion of arbitrary operations. Unobservable/failed pending outcomes remain Unknown. Onit delegates observation only for standard device/music tools; its general worker lifecycle is unchanged. See PLAN.md for crash-window evidence and limitations.

## Session contract

Reliability continuation (experiment 019): browser `audio_stop` is the immediate authoritative queue-stop acknowledgment and clears the local stopping flag. Delayed `playback_stopped_browser` telemetry updates status only; it must not clear newer audio. Playback stop/drain clears a failed turn's transient sink error so the next turn can recover. Explicit recognized `Stop speaking` produces no replacement task or speech; abandoned interruption currently remains stopped rather than automatically replaying. A cancelled ordinary adapter wait is recorded as unknown, not cancelled/completed, until independent reconciliation; no automatic retry. Bounded light corrections use a preceding successful typed receipt, and ambiguous `cancel that` asks for a target. These controls do not implement Onit background cancellation or acoustic echo handling.

States: IDLE -> ACTIVATING -> LISTENING -> THINKING/SPEAKING -> LISTENING; explicit exit or inactivity returns to IDLE. Listening and playback overlap during an active session. Wake detection must not require the user to repeat the phrase on every turn.

Preserve input pre-roll so activation does not clip the command following a wake phrase. Detecting speech is not proof that a conversational turn has ended; end-of-turn policy must tolerate brief pauses.

On barge-in: stop audible playback and clear queued audio promptly; cancel obsolete generation; discard stale results by session/turn identifiers; preserve the new user input. Store conversation history consistent with what was actually spoken. Track tool execution independently: cancellation of speech does not undo or repeat a completed action.

Echo cancellation uses playback reference audio or verified hardware support. Noise suppression and music ducking alone do not establish echo cancellation. Measure performance with speaker playback, not only headphones.

## MCP and streaming gate

Implemented HPC slice: MCP Python SDK 2.3.0, negotiated handshake protocol `2025-11-25` (explicit legacy initialization), Pipecat 1.13.0, ONNX Runtime 1.24.4. Full dependencies and hashes are in uv.lock. This establishes local interoperability, not Pi compatibility.

Our `asr` and `tts` processes each serve a single local client over stdio. No HTTP listener, auxiliary channel, shared audio service or external account is required. `python -B -m me3_voice.servers asr` and `... tts` run the mock-only servers. Standard output is reserved for MCP; diagnostics use stderr.

| Tool | Input | Result |
|---|---|---|
| `asr_open` | session_id, positive turn_id | operation_id, session/turn IDs, mode |
| `asr_append` | operation_id, zero-based sequence, pcm_b64 | next_sequence, session/turn IDs, optional partial text/final=false/revision |
| `asr_finish` | operation_id | session/turn IDs, final text, final=true, revision, mode |
| `tts_open` | session_id, turn_id, text (1–500 chars) | operation_id, session/turn IDs, mode |
| `tts_next` | operation_id | session/turn IDs, done; or sequence and pcm_b64 |
| `cancel` | operation_id | whether a live operation was removed; repeat is safe |

Both audio directions use base64 little-endian PCM16, mono, 16 kHz, at most 512 samples (32 ms) per chunk. Input sequences reject gaps and duplicates rather than silently repeating audio. Each server permits one active operation, at most 30 seconds of utterance/generated audio, with a 60-second lease checked on access/open. ASR starts a provider stream at open, accepts incremental audio and returns optional partials on append; finish commits a final transcript. The explicit BufferedASRStream compatibility adapter is final-only, not native streaming inference. TTS is pull-based: each next request advances the provider once, so no unbounded producer exists. The playback queue holds eight chunks (256 ms), plus an in-flight chunk and one provider chunk being processed. JSON/base64 and per-call overhead must be measured on Pi before choosing this as the production streaming path.

The client uses 15-second initialization/read deadlines, five-second per-tool deadlines by default, explicit release in finally blocks and stdio context teardown. In the live voice bridge, active reasoning and the containing turn have no wall-clock cutoff: they remain pending until completion, transport failure, explicit End, or a new accepted speech turn. The LLM connection and each SSE read are bounded by the configured provider timeout; there is no total-turn deadline. A connected response that stops emitting data therefore returns a provider-timeout error and listening resumes, while a response that continues streaming may run for as long as needed. ASR/TTS operations retain their configured deadlines. The browser selects adaptive engagement: followup defaults to 7 seconds after confirmed playback, explicit clarification to 18 seconds, extended mode to 20 seconds, and single mode returns to standby after the response. The legacy idle_seconds=60 setting only applies when adaptive mode is absent. Empty ASR restores the previous deadline; microphone telemetry and music playback do not extend it. Cancellation first invalidates the session/turn key, stops the cancellable sink and drains queued audio, then cancels generation and releases the remote operation. Late responses cannot update history or enter playback. A disconnected server requires recreating the client context; there is no automatic paid-request retry. Idle leases are lazy, not background timers; process teardown is the final resource fence.

`ConversationInput` maps VAD onset during THINKING/SPEAKING to session interruption while retaining the incoming PCM. Replay endpointing uses 320 ms pre-roll, 640 ms silence by default and a 30-second cap; the live browser bridge currently uses 1024 ms silence to tolerate natural pauses. These are provisional policy settings. Wake is detected from configured assets in connected application replay or the browser bridge; replay alone may instead use an explicitly labelled injected wake. Session.tick() remains the monotonic-clock hook for a future device loop. The finite recorded-audio application drives input-clock inactivity separately. The Pipecat bridge ingests continuous PCM in order with backpressure; the older endpointed demo remains a separate smoke path. Cancellation control belongs to Session outside the data queue.

History stores only completed text segments acknowledged by the sink. Memory writes retain `mock_sink_confirmed`; browser playback completion callbacks use `sink_confirmed`. Unacknowledged partial speech is omitted conservatively; browser callbacks still do not establish which words a listener heard. Browser output is capped at eight unacknowledged PCM chunks plus the Session's eight-chunk queue. On interruption the browser stops scheduled audio locally and sends an interrupt control; Session fences the old turn and flushes queued output. The standalone mock action ledger shields an operation from caller cancellation and rejects conflicting reuse of its key; it is in memory, bounded to 128 entries, and is neither a deployed task server nor a restart-safe exactly-once guarantee.

The existing ElevenASR/ElevenTTS source and tests are an unused offline adapter prototype, not the selected provider path. The user excluded ElevenLabs models on 2026-10-27. The selected DGX3 Qwen ASR/TTS contracts have completed bounded HPC software trials through ME3's MCP servers. Qwen2-Audio buffers each utterance for final-only recognition. General reasoning now routes through the installed Onit worker to the configured DGX `Qwen/Qwen3.8-27B` endpoint; there is no automatic OpenRouter fallback. Onit request count is provider-enforced by default, with an optional explicit cap for trials. One confined Onit-selected draft-write action and one synthetic end-to-end ASR→Onit→TTS replay passed. This does not establish broad Onit tool reliability, browser UI behavior, or Pi operation. Historical evidence remains unchanged.

### Long-task lifecycle status, 2026-11-02

ME3 Session has an optional `execute_background()` executor contract. It publishes a stable task ID, acceptance, named phase/steps, heartbeat, and terminal receipt through the existing sanitized transcript/event path. Speech interruption ends the current spoken turn but does not cancel the task; worker cancellation is a distinct operation. The voice bridge publishes transcript revisions over its active WebSocket, and the dashboard also reads persisted snapshots. A saved dashboard report says **Task at snapshot** and cannot reconnect to or resume the worker after a refresh/process loss.

Only the deterministic mock project worker currently implements `execute_background()`. The current `OnitTaskExecutor.execute()` still awaits the isolated Onit worker result, has no phase callback, and rejects another general Onit job while one is active. Returning an accepted reply from a detached Onit call alone would hide that serialization, so production Onit background execution remains pending. This in-process task callback is not MCP `notifications/progress` and does not implement the MCP Tasks extension's durable task handle or get/update/cancel methods. Do not infer production concurrent task/reasoning capability from mock lifecycle tests.

### Replaceable Pipecat PCM ingress, 2026-10-28

PipecatAudioInput owns one PipelineWorker/WorkerRunner for the entire file, with signal handling, RTVI and automatic turn tracking disabled. On input failure, deadline or cancellation the adapter becomes unusable, cancels its owned ingestion task, interrupts Session and cancels/joins the worker. Owning that task is necessary: a CancelFrame alone cannot release a system-frame handler blocked in ingestion. Failures are surfaced to the caller rather than silently dropping a packet or restarting effects.

Existing direct AudioApplication tests remain useful to isolate that framework boundary.

Closable LLM response streams yield bounded text segments or ToolCall(call_id,name,arguments); task results enter internal role=tool history and another bounded reasoning round. ### Live bridge service lifetime and budget scope

`VoiceRuntimeServices` owns one reasoning provider, one task executor and a pair of ASR/TTS MCP clients for the lifetime of the loopback bridge process. A new browser WebSocket gets a fresh conversational Session and transcript session, while provider request counters, MCP subprocesses, Onit task operations and remaining Onit request allowance stay attached to the bridge runtime. This prevents reconnecting the browser from resetting those in-memory limits. A process restart does reset them; use account-side quota controls for durable spend enforcement. Main reasoning requests and the optional Onit worker allowance are separately bounded and are not combined into one total cost ledger.

The speech MCP contexts are entered and exited on a dedicated asyncio owner task because the MCP stdio client uses AnyIO task-group cancellation scopes that must be closed by the same task that opened them. Session handlers call the shared MCP client over the in-process async streams. The browser bridge integration regression checks startup, browser disconnect and app cleanup.

The opt-in Onit worker receives only one bounded artifact-writing tool. Its completed files remain under ignored `var/scratch/onit-tasks/`; task receipts carry an allowlisted task ID and filenames.
